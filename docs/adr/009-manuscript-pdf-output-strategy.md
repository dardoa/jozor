# ADR-009: Manuscript PDF Output Strategy

## Status
Accepted (June 2026)

## Context
Sprint 18 proved that browser-rendered HTML/CSS is the right foundation for long-form family manuscripts. It handles Arabic shaping, RTL text, wrapping, fonts, and page-like preview much better than direct `jsPDF` text primitives.

The first implementation exports the manuscript by opening the generated HTML and relying on the browser print dialog. This was a useful proof of concept, but real PDF samples showed limitations:

- PDF quality depends on the user's browser, operating system, and PDF printer.
- Generated files may contain many Type 3 glyph warnings.
- Searchability, text selection, accessibility, and embedded font behavior are not guaranteed.
- Margins, headers, footers, page numbers, and print settings are controlled partly outside the app.
- The user experience is not yet a professional one-click export flow.

## Decision
Manual browser printing is a transitional output path, not the final manuscript PDF strategy.

For long-form family manuscripts, Jozor should keep HTML/CSS as the canonical print layout and add a controlled PDF generation backend around it:

```text
FamilyManuscriptModel
  -> HtmlManuscriptRenderer
  -> Preview inside the app
  -> Headless Chromium PDF renderer
  -> Downloaded manuscript PDF
```

The HTML manuscript renderer remains the shared source for preview and PDF output. The final PDF should be generated by a deterministic headless browser process, not by asking the user to manually print the preview.

## Rules
- `FamilyManuscriptModel` remains the source of truth for manuscript content.
- `HtmlManuscriptRenderer` remains the preferred long-form document renderer.
- Browser print preview can remain available for internal review and debugging.
- Production manuscript PDF export should eventually use a controlled headless renderer.
- `jsPDF` should remain focused on graphic/vector outputs such as posters, charts, tree diagrams, and compact reports.
- Markdown remains a content/interchange layer, not a PDF layout engine.

## Implementation Direction
The likely implementation path is:

1. Keep the current preview window and manual print path as a beta/internal fallback.
2. Add a server-side or controlled local API route that accepts the manuscript HTML or reconstructs the manuscript from safe inputs.
3. Render the HTML using headless Chromium/Playwright with fixed page settings, fonts, margins, and media mode.
4. Return a PDF blob to the app and record it through the existing publishing manifest/export-history pipeline.
5. Add automated checks that render representative small, medium, and real large manuscripts.

## Open Constraints
- Vercel serverless limits may affect Chromium size, startup time, and memory.
- A hosted browser rendering service or background job may be needed if direct serverless rendering is too heavy.
- Privacy rules must remain identical to preview/export rules: viewer output must use masked data only.
- The renderer must not accept arbitrary unsafe HTML from clients without a clear trust boundary.

## Non-Goals
This ADR does not implement the headless PDF renderer.

It does not remove the current preview or manual print flow. It only clarifies that this flow is transitional and should not be treated as the final professional PDF export.

## Consequences
- Future Sprint work should avoid polishing the manual print flow as if it were final.
- Preview UX remains valuable because it uses the same HTML manuscript renderer.
- A future sprint should introduce a "Controlled Manuscript PDF Export" path using headless Chromium or an equivalent controlled print engine.
- Manual QA should evaluate both visual correctness and PDF technical quality, including text selection/searchability and font embedding behavior.
